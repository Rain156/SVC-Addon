## 交付顺序

- **M0：工程基础。** 四个目标组合、明确模块边界、可重现构建、CI、测试和许可登记。
- **M1：语音管理。** 动态范围、蹲下／耳语、音量监测、指令、变声和群组；完成双玩家真实语音验收后才进入可玩 Alpha 发布。
- **M2：通讯设备。** 先交付对讲机、耳机与音响的完整闭环，再加入收音机、麦克风、调频机、支架和喇叭。四种构建维持同等功能，不给某版本打包空实现。
- **M3：客户端与录音。** 统一设备界面、头像动画、效果参数、资源导入、录制与播放。定义文件大小、时长、容量、删除与缺失资源处理。
- **M4：空间声学。** 方块材料衰减与区域规则。先实现有预算的直线路径，再评估绕射与路径搜索的性能收益。
- **M5：可选识别集成。** 外部 API 适配、关键词、超时、限流、取消和授权反馈；仅将命中结果映射到管理员预设命令。

## 后续设计原则

1. 频道使用 16 种颜色。显示名称与底层频道编号分离，避免把载入器枚举泄漏进公共 API。
2. 对讲机点对点直呼保留为联系人模式；与频道模式并存。被叫接受流程与头像设置在设备界面阶段实现。
3. 收发距离分别判断，并核对维度。半双工由服务端决定，断线、松键或租约超时都会释放频道。
4. 玩家禁言／禁听高于设备、广播与录音路由。私密群组语音不会自动成为广播输入；开放群组继续遵从 Simple Voice Chat 的开放规则。
5. 同一次输入对每位接收者只安排一次有效播放，避免频道桥接形成反馈回路。
6. 世界中的设备只持久化配置与资源引用。音频、识别队列和世界采样各自受限，不在音频回调中读磁盘或发 HTTP 请求。
7. 音频录制、外部识别与导入均需有明确的管理员配置和玩家反馈；当前版本没有这些数据收集或上传行为。
